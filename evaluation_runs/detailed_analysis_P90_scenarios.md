# 低速ノード割合90%シナリオ（P*_90_ON）の詳細分析レポート

## 概要

低速ノード割合が90%のシナリオ（P*_90_ON）において、REQUEST_BASEDモードでトラフィックが増加している原因を詳細に分析します。

## 問題の特定

### トラフィック増加が発生しているシナリオ

| シナリオ | NEIGHBORS_ONLY (bps) | REQUEST_BASED (bps) | 増加率 |
|---------|---------------------|-------------------|--------|
| P40_90_ON | 158,332,492 | 170,550,931 | **+7.72%** ⚠️ |
| P70_90_ON | 239,864,750 | 341,022,951 | **+42.17%** ⚠️ |
| P100_90_ON | 316,006,120 | 520,429,882 | **+64.69%** ⚠️ |

**注意**: P10_90_ONは実際にはトラフィックが削減されています（-80.59%）

### 2. トラフィック増加の原因分析

#### 原因1: 低速ノード間の要求・応答の増加

**問題点**:
- 低速ノード割合が90%の場合、高速ノードは10%しか存在しない
- 多くの低速ノードが高速ノードを見つけられない
- その結果、低速ノード同士で要求を送り合う

**動作パターン**:
1. 低速ノードAが高速ノードを見つけられない
2. 低速ノードAが隣接する低速ノードBに要求を送信
3. 低速ノードBも高速ノードを見つけられない場合、要求を記録するが応答できない
4. 低速ノードBが別の低速ノードCからコンテキストを受信
5. 低速ノードBが受信したコンテキストを低速ノードAに送信
6. このような低速ノード間の要求・応答が連鎖的に発生

**影響**:
- 低速ノード間の通信が増加
- 1つのコンテキストが複数の低速ノードを経由して伝播
- 送信回数が増加

#### 原因2: 低速ノードが受信したコンテキストを他の低速ノードに送信

**実装の動作**:
```java
// receiveSharedContext()内
if (broadcastScope == BroadcastScope.REQUEST_BASED && 
    nodeType == NodeType.FORERUNNER_LOW) {
  // 受信したコンテキストをローカルコンテキストとしても保存
  if (!localContexts.containsKey(blockIndex)) {
    localContexts.put(blockIndex, context);
  }
  
  // 他の低速ノードからの要求に応じて送信
  shareContextToRequestingNodes(context);
}
```

**問題点**:
- 低速ノードが受信したコンテキストを他の低速ノードに送信する
- 低速ノード割合が高い場合、この動作が連鎖的に発生
- 1つのコンテキストが複数の低速ノードを経由して伝播

#### 原因3: 高速ノードの不足による要求の集中

**問題点**:
- 低速ノード割合が90%の場合、高速ノードは10%しか存在しない
- 多くの低速ノードが同じ高速ノードに要求を送信
- 高速ノードが応答できない場合、低速ノード間で要求が増加

**影響**:
- 要求の集中による遅延
- 低速ノード間での代替的な要求の増加

### 3. P10_90_ONが削減されている理由

**P10_90_ONの特性**:
- Forerunner適用率: 10%
- 低速ノード割合: 90%
- **実際のForerunner適用低速ノード数**: 10% × 90% = 9%
- **実際のForerunner適用高速ノード数**: 10% × 10% = 1%

**削減されている理由**:
- Forerunner適用ノードが非常に少ない（10%）
- 低速ノード間の要求・応答が発生しにくい
- トラフィック量自体が少ない

### 4. 適用率が高い場合のトラフィック増加

**P40_90_ON、P70_90_ON、P100_90_ONの特性**:
- Forerunner適用率が高い（40%、70%、100%）
- 低速ノード割合が90%
- **実際のForerunner適用低速ノード数**: 適用率 × 90%
- **実際のForerunner適用高速ノード数**: 適用率 × 10%

**トラフィック増加の理由**:
- Forerunner適用ノードが多いため、低速ノード間の要求・応答が頻繁に発生
- 低速ノードが受信したコンテキストを他の低速ノードに送信する動作が連鎖的に発生
- 送信回数が増加

## 根本原因

### 1. 低速ノード間の要求・応答の連鎖

**問題**:
- 低速ノードが高速ノードを見つけられない場合、低速ノード同士で要求を送り合う
- 低速ノードが受信したコンテキストを他の低速ノードに送信する
- この動作が連鎖的に発生し、トラフィックが増加

**影響**:
- 送信回数が増加
- 受信回数も増加（低速ノード間の通信が増加）

### 2. 高速ノードの不足

**問題**:
- 低速ノード割合が90%の場合、高速ノードは10%しか存在しない
- 多くの低速ノードが高速ノードを見つけられない
- 低速ノード間での代替的な要求が増加

**影響**:
- 要求の集中による遅延
- 低速ノード間での要求の増加

### 3. 実装の動作特性

**問題**:
- 低速ノードが受信したコンテキストを他の低速ノードに送信する動作
- 低速ノード割合が高い場合、この動作が連鎖的に発生
- 1つのコンテキストが複数の低速ノードを経由して伝播

**影響**:
- 送信回数が増加
- トラフィックが増加

## 改善案

### 案1: 低速ノード間の送信を制限

**提案**:
- 低速ノードが受信したコンテキストを他の低速ノードに送信する動作を制限
- 例: 低速ノードは高速ノードからの要求にのみ応答する

**効果**:
- 低速ノード間の通信を削減
- トラフィックを削減

### 案2: 要求の重複を防止

**提案**:
- 同じブロックインデックスに対する要求を重複させない
- 例: 既に要求を送信したブロックインデックスには再要求しない

**効果**:
- 要求の重複を防止
- トラフィックを削減

### 案3: 高速ノードの優先使用

**提案**:
- 低速ノードは高速ノードを優先的に使用する
- 高速ノードが見つからない場合のみ、低速ノードに要求を送信

**効果**:
- 高速ノードの利用率を向上
- 低速ノード間の通信を削減

## 結論

低速ノード割合が90%のシナリオ（P*_90_ON）でREQUEST_BASEDモードのトラフィックが増加している主な原因は：

1. **低速ノード間の要求・応答の連鎖**: 低速ノードが高速ノードを見つけられない場合、低速ノード同士で要求を送り合う
2. **低速ノードが受信したコンテキストを他の低速ノードに送信**: この動作が連鎖的に発生し、トラフィックが増加
3. **高速ノードの不足**: 低速ノード割合が90%の場合、高速ノードは10%しか存在しないため、多くの低速ノードが高速ノードを見つけられない

特に、適用率が高い場合（P40_90_ON、P70_90_ON、P100_90_ON）でトラフィックが増加しており、適用率が低い場合（P10_90_ON）では削減されています。

改善案として、低速ノード間の送信を制限する、要求の重複を防止する、高速ノードの優先使用などの対策が考えられます。
