# 共有OFFシナリオで適用率による差が現れない理由

## 問題の概要

本番シナリオ（共有OFF）を実行した結果、Forerunner適用率（10%, 40%, 70%）による差が現れず、すべて同じ結果（伝播時間平均 5,311.94ms）になっています。一方、P100系のみ異なる結果（伝播時間平均 5,640.02ms）を示しています。

## 原因分析

### 1. シード値が固定されている

**現在の実行スクリプト**:
```bash
export SIM_SEED=10000  # 固定シード値
```

**影響**:
- すべてのシナリオで同じシード値を使用しているため、以下の要素が同一になります：
  - ブロック生成順序
  - ネットワーク構造（ノード間の接続関係）
  - トランザクションの生成タイミング
  - ランダム要素（遅延、ノード選択など）

**結果**:
- ネットワーク構造とブロック生成順序が同一のため、伝播時間も同一になる
- Forerunner適用率による違いは、各ノードのブロック処理時間の差として現れるが、伝播時間への影響は限定的

### 2. 共有OFF時の動作

**コード確認** (`ForerunnerNode.java`):
```java
// 共有OFF時: 高速/低速とも自前生成
if (!sharingEnabled) {
  ForerunnerNode.this.getFcm().generate(msg.getBlock());
}
```

**動作**:
- 共有OFFの場合、各ForerunnerNodeは独立して未来コンテキストを生成
- ブロック処理の高速化は適用される（`WEIGHTED_INVERSE_SPEEDUP`による）
- しかし、**伝播時間は主にネットワーク構造とブロック生成順序に依存する**

**影響**:
- Forerunner適用率が高いほど、ForerunnerNodeの数が増える
- 各ForerunnerNodeのブロック処理時間は短縮される
- しかし、伝播時間は「最初のノードから最後のノードまで伝播する時間」であり、これは主に：
  - ネットワーク構造（ノード間の接続関係）
  - ブロック生成順序
  - ネットワーク遅延
  に依存する

### 3. ブロック処理時間と伝播時間の関係

**ブロック処理時間**:
- ForerunnerNode: `base * nodeSpeedFactor * WEIGHTED_INVERSE_SPEEDUP`
- 非ForerunnerNode: `txCount * perTxUs * nodeSpeedFactor`

**伝播時間**:
- ブロックが最初のノードから最後のノードまで伝播する時間
- 主にネットワーク構造とブロック生成順序に依存
- ブロック処理時間の短縮は、各ノードでの処理遅延を短縮するが、伝播時間全体への影響は限定的

**例**:
- ネットワークが1000ノードで、ブロックが全ノードに伝播するのに5000msかかる場合
- 各ノードのブロック処理時間が10ms短縮されても、伝播時間への影響は小さい
- なぜなら、伝播時間は主にネットワーク遅延とノード間の接続関係に依存するため

### 4. なぜP100系だけ異なる結果になるのか

**P100系の特徴**:
- Forerunner適用率100% = すべてのノードがForerunnerNode
- すべてのノードでブロック処理時間が短縮される

**考えられる理由**:
- すべてのノードがForerunnerNodeの場合、ブロック処理時間の短縮が累積的に影響する可能性
- または、シード値による偶然の差（1回実行では統計的な差が現れにくい）

## 以前の結果と異なる理由

### 以前の実行条件の推測

以前の実行では、以下のいずれかが異なっていた可能性があります：

1. **異なるシード値を使用**
   - 各シナリオで異なるシード値を使用していた
   - ネットワーク構造やブロック生成順序が異なっていた

2. **複数回実行による統計的な差**
   - 50回実行など、複数回実行していた
   - 統計的な差が現れていた

3. **異なる実行条件**
   - ブロック数、ノード数、ネットワーク設定などが異なっていた

### 現在の実行条件

- **シード値**: 固定（10000）
- **実行回数**: 各シナリオ1回
- **ブロック数**: 50ブロック
- **ノード数**: 1000ノード

## 解決策

### 1. 異なるシード値を使用する

各シナリオで異なるシード値を使用することで、ネットワーク構造やブロック生成順序が異なり、適用率による差が現れる可能性があります。

```bash
# シナリオごとに異なるシード値を使用
export SIM_SEED=$((10000 + scenario_num * 1000))
```

### 2. 複数回実行する

各シナリオを複数回実行し、統計的な差を確認します。

```bash
# 各シナリオ50回実行
for run_num in {1..50}; do
  export SIM_SEED=$((10000 + run_num * 1000))
  # 実行...
done
```

### 3. ブロック処理時間を直接測定する

伝播時間ではなく、ブロック処理時間を直接測定することで、適用率による差を確認できます。

## 結論

**現在の結果が同じになる理由**:
1. **シード値が固定**されているため、ネットワーク構造とブロック生成順序が同一
2. **1回実行**では統計的な差が現れにくい
3. **共有OFF**の場合、ブロック処理時間の短縮は伝播時間への影響が限定的

**以前の結果と異なる理由**:
- 以前は異なるシード値や複数回実行を使用していた可能性が高い

**推奨される対応**:
- 各シナリオで異なるシード値を使用する
- または、複数回実行して統計的な差を確認する
